# F-M2-1 — The documented prerequisites silently disable the upstream compatibility proof

| Field | Record |
|---|---|
| **1. What failed** | An environment built from the documented prerequisites (`pip install -e ".[train,dev]"` plus `docs/REPRODUCTION.md` Stage 0) cannot import `vint_train.training.train_utils`, because that module imports `matplotlib` and `cv2` at module level and neither is a declared dependency. The 26 `upstream`-marked tests — the compatibility proof that the standing instructions call the specification — degrade to **9 passed, 6 skipped, 11 not collected**. The suite still exits 0 and reports "228 passed". |
| **2. How detected** | M2, by running the suite under the newly built canonical environment and comparing counts against the previous environment: 245/26 became 228/9. Not caught by CI or by any gate, because a skip is not a failure and the headline number still looked green. |
| **3. Claim threatened** | Standing rule 2 — that any change to the format modules is validated against the reference loader's behaviour. In an environment built to the documented instructions, that validation was substantially not running. Also `gates/M1/`'s "26 are upstream-marked and run against the pinned reference clone", which was true of the environment M1 used and not of the one the docs describe. |
| **4. Source** | environment |
| **5. Correction** | `matplotlib>=3.8` and `opencv-python-headless>=4.9` added to the `train` extra in `pyproject.toml`, with the reason recorded inline so the next reader does not prune them as unused — this package imports neither. Headless opencv deliberately: the pinned `opencv-python==4.6.0.66` has no wheels for Python ≥ 3.11 and its PyQt5 conflict aborts the process (`docs/REPRODUCTION.md` landmine table). |
| **6. Pre-registered?** | No. This is infrastructure, not a registered analysis. |
| **7. Results changed?** | None. No result had been produced in the canonical environment — the defect was found while verifying that environment, before gate G0.c ran. Had it not been found, G0.c would have executed in an environment where the compatibility proof was 65 % inert, and the gate archive would have recorded a passing suite as evidence. |
| **8. Residual uncertainty** | The fix makes the *declared* dependency set sufficient on this machine. Whether it is sufficient on a clean machine is exactly what the Task 5 archive regeneration tests, and that test is the evidence — not this record. It is also unknown how long the gap existed: `.venv-m1` had both packages transitively, so every prior local run was unaffected, and the gap would only ever have appeared on a fresh install. |
| **9. Gate blocked or reopened** | No gate blocked. G0.c had not yet run; this was found during its environment preparation. |

## Why a skip is worse than a failure here

A failing test stops a gate. A skipping test lets the gate proceed and writes
a green summary into the archive, and the archive then reads as evidence that
the proof ran. The count is the only thing that distinguishes the two, and
nothing was comparing counts across environments until an environment change
forced the comparison.

This is the same class as [F-M1-1](F-M1-1.md) — a documented procedure that
does not do what its documentation claims — but it fails in the more dangerous
direction. F-M1-1 exited 1 and was impossible to miss. This one exits 0.

The standing rule that gate scripts must *preflight and refuse* rather than
infer execution state has an analogue here that is not yet implemented: a
verification run should assert the expected number of upstream-marked tests
rather than trusting that a green suite means the proof ran. Recorded as a gap,
not as a fix.
