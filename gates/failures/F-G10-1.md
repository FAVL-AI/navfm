# `F-G10-1` — predicted and realised G10 are not commensurable

**Status: OPEN. Blocks BO-10 trajectory admission.** Found 2026-09-10 on the
first successful production episode.

## What happened

The collection pipeline ran end to end and produced a clean trajectory. Every
post-episode gate passed except one:

| gate | result |
|---|---|
| G8 controller identity | PASS |
| G9 goal image seal | PASS — goal is not the final observation |
| MOTION_REALISED | PASS — travelled 20.968 m |
| data integrity | PASS — 740 frames, 740 images, all finite |
| **G10 realised** | **FAIL — heading_changes** |

Realised: 740 frames, 20.968 m travelled, 12.833 m separation, 729 NoMaD
windows — every threshold met **except turns**, which measured **1** against a
requirement of 3.

The same route measured **3** turns when predicted from the planned polyline
(73.0°, 30.6°, 34.2°) and **1** when measured from the driven path (172.2°).

## Root cause

The two are computed over structurally different geometry.

**A planned route is a piecewise-linear polyline** with genuine straight legs
between corners. **A driven path is continuously curving**, because pure pursuit
steers toward a moving lookahead point and never travels exactly straight.

Measured on the driven path, decimated at 0.5 m:

```
decimated segments                41
near-straight segments (<1°)       1
per-segment heading delta      min 0.82°   median 3.86°   max 19.90°
```

The counting rule closes a turn episode only when it meets a straight segment.
With one near-straight segment in 41, essentially all turning merges into a
single 172° episode.

That grouping rule is not itself wrong — it was introduced on 2026-09-09
(`amendment_heading_change_counting_20260909.md`) to stop a corner splitting into
two counts when it fell between decimation samples, and it does that correctly on
planned polylines. Applied to a driven path it does the opposite: it merges
distinct corners because the straightness that separated them is gone.

So `predict_from_route` and `measure_from_trajectory` share a threshold and a
counting rule while operating on representations for which that rule behaves
differently. **The prediction is not a valid forecast of the realisation**, and
the gate's own labelling of one as `PREDICTED_CAPABILITY` and the other as
`POSTCONDITION` was correct about their status but did not make them
commensurable.

## What must NOT be done

- **Do not lower the turn threshold.** It is frozen, and it was met by the route.
- **Do not change `straight_deg` or the grouping rule now.** Both would be tuning
  a measurement definition after seeing the outcome it produced, which is the
  defect this programme has spent several tranches avoiding.
- **Do not retry with route 083 or 086.** No frozen retry policy exists, and the
  cause is systematic rather than route-specific: any pure-pursuit realisation of
  any route will be continuously curving. Both would be expected to fail the same
  way, and trying them until one passes would be optional stopping.

## What this does NOT invalidate

- `KINEMATIC_COLLECTION_DRIVE_V1`. 740 poses applied, 0 collision rejections,
  20.968 m realised against 20.808 m planned. The drive works.
- Route admission. The route satisfied the contract as planned.
- The obstacle map acceptance, G3–G9, or either frozen route-set.
- The trajectory data itself, which is well formed: 740 images matching 740
  poses, all values finite, goal image distinct from the final observation.

## Resolution requires a dated amendment, made before any retry

The amendment must decide what the turn requirement means for a *driven* path,
and state it before another trajectory is collected. Candidate directions, none
of which is chosen here:

1. Define the realised turn count over the **planned** route the episode
   followed, treating the driven path as tracking error — cheap, but then G10
   measures the plan rather than the data.
2. Define a driven-path turn criterion on its own terms — for example cumulative
   absolute heading change, or turns separated by a *low-curvature* run rather
   than a strictly straight one — with its own frozen parameters and controls.
3. Keep both and require both, making the prediction a genuine precondition and
   the realisation a genuinely different postcondition.

Whichever is chosen must be preregistered with its own defining controls, and it
must be validated on a driven path that is already known to fail and one already
known to pass, so it cannot be a rule shaped to admit this particular trajectory.

## Correction — total path length does not rule out corner-cutting

An earlier reading of this finding stated that local corner-cutting was ruled out
because the realised path is **0.8% longer** than planned (20.968 m against
20.808 m). That inference is withdrawn.

A controller can cut corners locally while still producing a longer total path:
tracking oscillation, overshoot and curvature elsewhere add length back. Total
path length is an aggregate and cannot isolate a local behaviour.

The defensible statement is narrower:

> The observed total path length does not support the hypothesis that simple
> **global** path-shortening alone explains the blending. **Local corner-cutting
> remains possible and has not been isolated.**

`SYSTEMATIC_TURN_BLENDING` therefore keeps every candidate cause open — local
corner-cutting, lookahead-induced blending, cross-track oscillation, overshoot,
route geometry, the route-to-controller interface, or a mixture — and stays
classified **UNRESOLVED**.

This is the same class of error the programme has repeatedly found in its own
instruments: an aggregate quantity used to answer a question about a local event.
It is recorded here rather than silently edited out.
