# F-M2-2 — A sourced ROS 2 environment silently overrides the canonical interpreter's imports

| Field | Record |
|---|---|
| **1. What failed** | `/opt/ros/humble/setup.bash`, sourced from the shell profile on this machine, exports `PYTHONPATH=/opt/ros/humble/lib/python3.10/site-packages:/opt/ros/humble/local/lib/python3.10/dist-packages`. A virtualenv does **not** isolate an interpreter from `PYTHONPATH`, and those entries are *prepended* to `sys.path`. The Python 3.11 canonical environment therefore imported from another interpreter's 3.10 site-packages. The whole test suite failed at collection with `ModuleNotFoundError: No module named 'lark'` — an error naming a package nobody in this project depends on, raised from a ROS launch module that had shadowed a real import. |
| **2. How detected** | M2, on the first attempt to run the suite under the newly built canonical environment. The symptom named neither ROS nor `PYTHONPATH`, which is what made it worth recording. |
| **3. Claim threatened** | Every claim resting on "the gate ran in the canonical environment". The environment identity introduced in this session (`navfm.provenance`) covered python, torch, cuda, the installed-distribution digest, OS and architecture — and would have reported an **identical `environment_id`** for a contaminated shell and a clean one, because none of those fields moves when `PYTHONPATH` changes. The identity would have certified two different instruments as the same one. |
| **4. Source** | environment |
| **5. Correction** | Two parts. `PYTHONPATH` is now a field of the environment identity and is hashed into `environment_id`, so a contaminated shell produces a different identity and a regeneration comparison fails loudly instead of matching. It is also surfaced on the fingerprint's page-one block, so a reader sees it without computing anything. `docs/REPRODUCTION.md` gains the landmine row. Operationally, the training environment is run with `PYTHONPATH` unset. |
| **6. Pre-registered?** | No. Infrastructure. |
| **7. Results changed?** | None. Found before gate G0.c executed. Had it not been, the gate would have run against a mixed 3.10/3.11 import path while its own archive certified a clean 3.11 canonical environment — and the archived `environment_id` would have been indistinguishable from the honest one. |
| **8. Residual uncertainty** | `PYTHONPATH` is the leak this machine exhibits; it is not the only possible one. `PYTHONHOME`, `PYTHONSTARTUP`, `sitecustomize.py` on the path, and `pip install --user` packages under `PYTHONNOUSERSITE`-unset interpreters can all change which code runs without moving any currently-hashed field. The identity now covers the one that actually bit; it does not claim to cover the class. |
| **9. Gate blocked or reopened** | No gate blocked. Found during environment preparation, before G0.c. |

## Why the identity had to change, not just the runbook

A note in the runbook saying "unset `PYTHONPATH`" would have been the cheap
fix, and it would have left the failure mode fully armed: a reader who missed
the note gets a gate archive whose `environment_id` matches the canonical one
while the interpreter is importing from a different Python.

The rule the identity encodes is that **anything which changes what code runs
is part of the instrument**. `PYTHONPATH` changes what code runs. It belongs in
the hash for the same reason the torch version does, and its absence was a
defect in the identity's definition rather than an oversight in the
documentation.

That this was found within an hour of the identity being written is the
argument for archiving identities at all: the field that was missing announced
itself the first time the identity met a real environment.
